# 批量生成激活码「无响应 → 504」排查报告

> 日期：2026-11-02 10:20  
> 现象：填写 1000 个、批次 `LDXP001`、备注「链动小铺激活码」→ 点「生成」无任何反馈 → 约 1 分钟后 toast「请求失败 504」

---

## 一、结论先说

**功能确实有问题，而且不是"没生效"，而是"数据已经写进库了，前端却告诉你失败"。**

线上库现在真实存在 **244 条 `LDXP001` 批次激活码**（你要的是 1000 条），它们是在 10:17:53 和 10:18:18 分两次写进去的。如果当时再点一次「生成」，就会又多出一批——这是当前最危险的地方。

---

## 二、根因链（三个问题叠加）

### 问题 1（根因）：后端逐条 INSERT，200 条要 40 秒以上

`sync-worker/src/admin.ts` 的 `createActivationCodes` 是 **for 循环里逐条 `await`**：

```ts
for (const c of codes) {
  await db.prepare(`INSERT INTO activation_codes ...`).bind(...).run()  // 每条一次 D1 往返
}
```

实测：线上生成 **20 个码耗时 4.64 秒**，即 **每条约 230ms**。200 条 ≈ **46 秒**，必然撞网关超时。

### 问题 2：输入 1000 被静默改成 200

- 前端 `<input type="number" max="200">` 的 `max` **不会阻止手动键入 1000**，也不会提示；
- 后端 `int(body.count, 1, 200, 10)` 把 1000 **静默截断为 200**。

所以即使一切正常，你点「生成 1000」也只会得到 200 个，而界面上没有任何提示。

### 问题 3：代理层对写请求做自动重试，导致"写了两遍"

`release/server.js` 的 `proxyApi` 是"每个上游最多尝试 2 次"：

```js
for (let attempt = 1; attempt <= 2; attempt++) { await send(upstream, payload) ... }
```

它**不区分 GET 和 POST**。这次的完整时间线正好对上：

| 时刻 | 事件 |
| --- | --- |
| 10:17:53 | 第 1 次尝试开始，`created_at` 记为 02:17:53Z；Worker 写了 124 条后，server.js 的 `AbortSignal.timeout(25000)` 到点，请求被中断 |
| 10:18:18 | 25 秒后 server.js 自动重试（第 2 次），`created_at` 记为 02:18:18Z；又写了 120 条，再次被 25s 超时中断 |
| 之后 | 换第二个上游继续重试，最终托管平台前置网关先到 60s 上限，返回 504 给浏览器 |

两次 `created_at` 相差**正好 25.0 秒**，就是 `AbortSignal.timeout(25000)` 留下的指纹。244 = 124 + 120，两次残留之和。

### 问题 4（体验）：点击后完全无反馈

`showGenModal` 里的「生成」按钮，`onclick` 只 `await api(...)`，**没有 disabled、没有 loading、没有文案变化**。请求要跑几十秒，用户只能干等，自然分不清"在跑"还是"卡死"。

## 四、修复方案

### A. 后端：批量插入（根治）

`createActivationCodes` 改为 D1 `db.batch()`，每批 50 条：

```ts
for (let i = 0; i < codes.length; i += 50) {
  const stmts = codes.slice(i, i + 50).map((c) =>
    db.prepare(`INSERT INTO activation_codes (code, batch, note, status, created_at) VALUES (?, ?, ?, 'unissued', ?)`)
      .bind(c.code, c.batch, c.note, c.createdAt))
  const res = await db.batch(stmts)
  created += res.filter((r) => r.success).length
}
```

预期：200 条从 ~46s 降到 **1 秒级**；1000 条约 2-3 秒。这也是能不能把上限提到 1000 的前提。

> 注意：`batch()` 是事务性的，单条主键冲突会让整批失败。因此需要保留"逐条兜底"：某批失败时退回逐条插入（当前的重号跳过逻辑不能丢）。

### B. 前端：加反馈 + 真校验

1. 「生成」点击后立即 `disabled` + 文案变「生成中…（200 个）」，并禁用「取消 / ✕」，防重复提交；
2. 数量输入框失焦/提交时校验：`> 200`（或新上限）直接 toast 提示，不再静默截断；
3. 请求超过一定时长（如 15s）在按钮上加「仍在生成，请勿关闭…」；
4. 失败提示补一句运营能自救的话：「请先回到列表确认该批次是否已生成，避免重复创建」。

### C. 代理：写请求不自动重试

`release/server.js` 改为只对 `GET/HEAD` 重试，`POST/DELETE` 单次直达（超时原样返回 502/504）。这样即使再遇到慢请求，也不会重复写库。

### D. 数量上限

需要你定：单次上限维持 **200**，还是提到 **1000**（批量插入后性能没问题，1 秒级）。前端提示文案同步改。

## 五、修复与上线结果（2026-11-02 10:40 已完成）

### 5.1 代码改动

| 文件 | 改动 |
| --- | --- |
| `sync-worker/src/admin.ts` | `createActivationCodes` / `issueActivationCodes` / `deleteActivationCodes` 全部改为 `db.batch()` 每 100 条一批，批量失败时退回逐条（保留"重号跳过"语义） |
| `sync-worker/src/index.ts` | 单次生成上限 `200 → 5000`；发放/删除单次上限 `500 → 5000` |
| `release/server.js` | 只对 `GET/HEAD` 重试，`POST/PUT/DELETE` 单次直达且失败不换上游；写请求超时 `25s → 55s` |
| `release/admin/index.html` | 数量上限 5000 + 提交前显式校验；生成中锁定整个弹窗（「生成中…（N 个）」+ 输入框/取消/✕ 全禁用）；实际生成数少于请求数时提示；「立即发放本批」加加载态；`.code-out` 加 `white-space: pre-wrap`（原来 5000 个码会横排成一坨）；导出改并发 3 页拉取 |

### 5.4 线上验证

- 生成弹窗标题为「数量(1-5000)」；输入 6000 点生成 → 提示「数量需为 1-5000 的整数」，**不发请求**，弹窗保持；

- 全程无 console 报错。

### 5.5 结论

原「点生成没反应 + 504」的三个成因（逐条写库、静默截断、写请求重试）已全部消除。现在 5000 个约 20 秒内完成，期间界面明确显示「生成中…（5000 个）」；即使再遇到网络超时，因为写请求不再重试，也不会重复建批次。

## 六、后续可选优化

- 若单次还要更大（如 2 万），建议改成"服务端异步任务 + 前端轮询"，不要继续拉长同步请求；
- 生成成功后弹窗里的「复制全部」在 5000 条时约 150KB，剪贴板无压力；
- 大批量删除仍按前端 500/批，服务端已支持单次 5000。
