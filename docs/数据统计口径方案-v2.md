# 数据统计口径方案 v2（2026-10-27）

> 目标：让后台「数据概览」的每个数字都能被独立解释，且漏斗各层不再自相矛盾。
> 现状问题不是 SQL 写错，而是**四个指标用了四套互不相干的身份标识**，被拼成了一条漏斗。

---

## 一、现状诊断（为什么现在的数不可信）

当前唯一身份来源是 `analytics_events.visitor`，但两端含义不同：

| 端 | visitor 是什么 | 稳定性 |
|---|---|---|
| App | `~/.ticktask/config.json` 里的 deviceId（一台机器一个 UUID） | 好（清缓存/重装不变），但**不认账号** |
| 下载站 | 浏览器 `localStorage['todobar-site-vid']` | 差（换浏览器/清缓存/无痕即新设备） |

由此产生的具体错误：

1. **访客数 96 虚高**
   下载站没有服务端/指纹兜底，只靠 localStorage。清一次缓存、换个浏览器、开无痕都算新访客。

2. **点击数 19 比访客数 96 还少 —— 事件在丢失**
   `/api/track` 经 `release/server.js` 反代时**没有透传客户端 IP**，Worker 只看到容器出口 IP；而 `trackAllowed(ip)` 是 180 次/分钟的单 IP 限流，**全站所有访客共用这一个桶**，高峰期直接 `skipped:true` 静默丢弃事件。这是"点击少于访客""曲线锯齿"的直接原因。

3. **安装数 50 > 点击数 19 —— 两个数不在同一坐标系**
   安装数取的是 App 端 deviceId，与下载站 visitor 完全不同的域，不可能构成上下级；且安装来源本就包含旧渠道、朋友分享、U 盘拷贝。硬拼成"漏斗"，数学上必然荒谬。

4. **注册数 1 口径错位**
   `overviewStats` 里 `registrations` 实际取的是 `users` 表在窗口内的新增数，与"安装后完成注册"无关，也没有和安装设备建立任何关联。

5. **活跃用户按设备计，不按人计**
   `COUNT(DISTINCT visitor) WHERE event='app_open'`。同一账号在两台电脑登录 = 2 个活跃用户。

6. **工具内页面访客**同样是 deviceId 去重。方向正确，但缺少"重装后仍识别同一台机器"的硬件指纹兜底。

## 二、新身份体系（三层）

所有指标统一从这三层派生，不再各写各的。

| 层 | 字段 | 取值 | 作用 |
|---|---|---|---|
| 账号 | `uid` | `users.id`，未登录为空 | **去重第一优先**：已登录一律按账号算 |
| 设备 | `device` | 设备指纹 hash（32 位），见下 | 未登录时的去重主体；跨端归因的锚点 |
| 会话 | `sess` | 站点端 `sessionStorage` 会话 ID | 只用于"进入次数"，不参与去重 |

**device 怎么来（真正的设备指纹）**

- **App 端**：`sha256(MachineGuid + 固定盐)`。Windows 的 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` 重装系统前不变 → 重装 App、清 WebView 数据、换 deviceId 都能认出同一台机器。读不到时回退到持久化 deviceId（Rust 侧已有 `winreg` 依赖，无新依赖）。
- **站点端**：`sha256(cookie/localStorage 持久 ID + 浏览器特征)`。浏览器特征取 Canvas 渲染 hash、WebGL vendor、`hardwareConcurrency`、`deviceMemory`、屏幕分辨率+色深、时区、语言。持久 ID 改为 **localStorage + Cookie 双写**（1 年），任一存活即可恢复；两者都无时用特征 hash 兜底合并。

**身份缝合（同一台设备登录前后算一个人）**

新增 `identity_links(device, uid)`：任何一次登录上报都把 device 与 uid 绑定并长期保存。统计取主体表达式：

```sql
subject = 'u:' || COALESCE(NULLIF(e.uid,''), l.uid)        -- 已登录 / 该设备曾登录
        | 'd:' || e.device                                  -- 从未登录
```

效果：用户上午未登录使用、下午登录，同一天只算 1 个活跃用户。

## 三、指标口径定义（新）

北京时间日界（`date(ts,'+8 hours')`），窗口默认近 30 天。

| # | 指标 | 定义 | 去重主体 | 关键约束 |
|---|---|---|---|---|
| 1 | 日活跃用户 DAU | 当天有 `app_open` 的用户数 | `subject`（账号优先，其次设备） | 同账号多设备 = 1 |
| 2 | 周/月活跃 WAU/MAU | 近 7 / 30 天同上 | `subject` | 滚动窗口去重 |
| 3 | 下载站访客数 | 窗口内到过下载站的设备数 | `device` | **30 天内同设备多次进入 = 1** |
| 4 | 访问次数 | 设备进入下载站的累计次数 | 不去重 | 一次会话（进入）计 1，页内点击/滚动不计 |
| 5 | 下载设备数 | 下载按钮点击过的设备数 | `device` | 同设备多次下载 = 1 |
| 6 | 安装设备数 | 首次运行上报过 `install` 的设备数 | `device`（硬件指纹） | 同设备重复上报 = 1 |
| 7 | 注册用户数 | 完成注册且**所在设备有安装记录**的用户数 | `uid` | 必须发生在安装之后 |
| 8 | 工具内页面访客 | 该页面 `page_visit` 的设备数 | `device` | 页面级独立设备 |
| 9 | 功能点击 | `feature_click` 事件条数 | 不去重 | 真实点击次数 |

**关于第 4 项（原"点击数"）**
你的原话是"进入 1 次算 1 次，不管页内点了多少下"。所以它本质是**访问次数（次）**，不是人数。它和上下相邻的"设备数/账号数"不是同一量纲，硬塞进递减条会再次出现"第二层比第一层高"。
建议：漏斗只保留人数链（访客设备 → 下载设备 → 安装设备 → 注册账号），"访问次数、人均访问 X 次、下载点击次数"作为第一层的副文本展示。文案也从"点击数"改为"访问次数"。

## 四、漏斗如何保证不自相矛盾（关键设计）

即使每一层口径都对了，`访客设备 30 / 安装设备 50` 依然会出现——因为安装来源不止下载站。
要让漏斗成立，安装必须**可归因**：

1. `release/server.js` 新增 `/download/:file` 路由：浏览器点下载时，服务端记录 `{device, ip, ua, ts}` 到 `site_downloads`，然后 302 到真实安装包（保留 `?v=` 缓存击穿）。
2. `release/server.js` 反代时**透传真实客户端 IP**（`x-forwarded-for` / `cf-connecting-ip` → `x-client-ip`），Worker 优先读它。这一步同时修掉第 1 节第 2 条的"全站共享限流桶"。
3. App 首次运行上报 `install` 时，Worker 用 `(该设备 IP, 24 小时窗)` 匹配最近一条 `site_downloads` → 标记 `attributed_device`。
4. 漏斗"安装数"= 可归因安装；未匹配到下载记录的安装单独显示为"其他来源安装 N 台"，不计入漏斗条。注册数同样限定在可归因安装的链路上。

这样四层严格单调：访客设备 ≥ 下载设备 ≥ 归因安装 ≥ 归因注册。

**精度边界（必须知情）**：NAT/公司网络下同 IP 多人会误归因；VPN 会断链。因此标注"可归因安装"，不宣称绝对精确。

## 五、数据模型变更

```sql
-- 0006_analytics_identity.sql
ALTER TABLE analytics_events ADD COLUMN uid    TEXT NOT NULL DEFAULT '';
ALTER TABLE analytics_events ADD COLUMN device TEXT NOT NULL DEFAULT '';
ALTER TABLE analytics_events ADD COLUMN sess   TEXT NOT NULL DEFAULT '';
CREATE INDEX IF NOT EXISTS idx_events_device ON analytics_events(device, ts);
CREATE INDEX IF NOT EXISTS idx_events_uid    ON analytics_events(uid, ts);

CREATE TABLE IF NOT EXISTS identity_links (
  device     TEXT PRIMARY KEY,
  uid        TEXT NOT NULL,
  first_seen TEXT NOT NULL,
  last_seen  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_identity_uid ON identity_links(uid);

CREATE TABLE IF NOT EXISTS site_downloads (
  id     INTEGER PRIMARY KEY AUTOINCREMENT,
  device TEXT NOT NULL,
  ip     TEXT NOT NULL DEFAULT '',
  ua     TEXT NOT NULL DEFAULT '',
  ts     TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_dl_ts ON site_downloads(ts);
```

历史数据：旧行 `device = visitor` 回填（App 端 visitor 就是设备 ID，语义等价），`uid` 留空；能从当前 `sessions` 反查到的补 `identity_links`。页面上标注"新口径自 2026-10-27 生效"，趋势图不断档。

## 六、采集端改造

**App（`src/analytics.ts` + Rust）**
- 每条事件附 `uid`（登录后才有，来自 `account.ts` 的 account.user.id）与 `device`（硬件指纹）。
- 新增 Rust 命令 `device_fingerprint()`：读 MachineGuid → sha256(盐+guid)，读不到返回空（服务端回退 visitor）。
- `install` 标记从 localStorage 迁到 `~/.ticktask/config.json`，避免清缓存重复报安装。
- ⚠️ **需发新版 App 才生效**；旧版本上报的数据只能按设备计，账号去重率随装机覆盖率上升。

**下载站（`release/index.html`）**
- 内联指纹脚本（零第三方、零 CDN）：canvas/webgl/硬件/时区 → hash，与持久 ID 组合成 `device`。
- 持久 ID 改 localStorage + Cookie 双写。
- 会话：`sessionStorage` 会话 ID，30 分钟静默过期；**每次进入上报 1 条 `site_visit`**（替代原 `pageview`，语义即"一次进入"）。
- 下载链接改为 `/download/Tacco-setup.exe?...&d=<device>`，由 server.js 记录后跳转。

**Worker（`sync-worker/src/index.ts`）**
- `/api/track` 接收并落库 `uid` / `device` / `sess`；`source` 增加 `dl`。
- 限流键从 `ip` 改为 `device || ip`，阈值按设备 60/分钟（不再全站共享一个桶），丢弃次数写日志便于排查。
- 登录接口（register/login）成功时 upsert `identity_links`。

## 八、实施顺序

1. Worker：迁移 + 落库字段 + 限流修复 + 统计 SQL 重写（`admin.ts` 全部改为 subject/device 口径）
2. server.js：IP 透传 + `/download` 路由
3. 下载站：指纹脚本 + 会话 + 下载链接
4. App：uid/device 上报 + MachineGuid 命令 → 发 0.4.55
5. 后台：图表文案与漏斗结构
6. 上线后核对：访问次数 ≥ 访客设备数 ≥ 下载设备数 ≥ 归因安装 ≥ 归因注册

> 说明：1–3、5 项当天可上线并立即改善数据质量；第 4 项需随版本发布，账号去重从新版装机后开始积累。

## 九、需要你决策的三点

1. **安装归因**：是否按第四节做跨端归因（需改下载链接走 server.js 中转）？不归因的话，安装数只能与下载站指标并列展示，不能画进漏斗。
2. **访问次数**：按建议放在漏斗第一层副文本（推荐），还是坚持作为漏斗第二层单独一条（会出现第二层高于第一层）。
3. **历史数据**：旧数据按 `device = visitor` 回填后继续展示（趋势连续、新旧口径混合），还是从生效日起重新起算（口径纯净、趋势断档）。
