# TickTask 账号体系 + 买断制激活方案（设计稿 v2，已确认）

> 原则：零新增成本（全部复用现有 Cloudflare Worker + D1 + KV）；服务端校验为主（客户端校验只能防君子）；兼容现有用户数据，平滑迁移。

---

## 一、总体架构

```
桌面应用 TickTask
   │  (HTTPS, 国内可直连走 todobar-app.app.workbuddy.host 代理,
   │   海外/VPN 用户走 sync.tuanzhang.site 直连)
   ▼
Cloudflare Worker（唯一的后端）
   ├─ D1: users / sessions / activation_codes / tasks / birthdays ...
   ├─ KV: 会话令牌缓存
   └─ /api/auth/*  /api/activate  /api/tasks  /api/admin/*
```

不引入任何第三方账号服务（Supabase/Auth0 等），账号逻辑全部自研在 Worker 里，约 200 行代码。

## 二、账号体系

### 2.1 数据表（新增 3 张，自动建表）

| 表 | 字段 | 说明 |
|---|---|---|
| users | id, email, password_hash, salt, email_verified, activated, activated_at, created_at, disabled | email 唯一，注册需邮箱验证码 |
| email_codes | email, code_hash, purpose(register/reset), expires_at, attempts, created_at | 验证码：10 分钟有效、最多 5 次尝试、同邮箱 60 秒一封 |
| sessions | token, user_id, device_name, device_id, created_at, last_seen_at, expires_at | 每台设备一个会话，上限 3 台 |
| activation_codes | code, status(unused/used/revoked), bound_user_id, bound_at, batch, note | 激活码与账号一对一绑定 |

### 2.2 密码安全

- WebCrypto `PBKDF2-SHA256`，每用户独立盐，10 万次迭代（Workers 原生支持，免费额度够用）。
- 数据库只存 hash+salt，泄露也无法还原密码。

### 2.3 接口

| 接口 | 说明 |
|---|---|
| POST /api/auth/send-code | 发送邮箱验证码（purpose=register/reset；60s 频控+按 IP 限流） |
| POST /api/auth/register | 邮箱+密码+验证码注册，返回会话令牌 |
| POST /api/auth/login | 登录，返回会话令牌（绑定设备，超过 3 台时提示先解绑） |
| POST /api/auth/logout | 注销当前设备会话（= 解绑本机，释放额度） |
| GET /api/auth/devices | 当前账号的设备列表（设备名/最近活跃/当前设备标记） |
| POST /api/auth/devices/revoke | 解绑指定设备（远端踢下线，释放额度） |
| POST /api/auth/password | 修改密码（需邮箱验证码；改密后其它设备会话全部失效） |
| GET /api/auth/me | 查询当前账号状态（是否已激活、设备列表、试用剩余天数） |

### 2.4 数据隔离（回答"数据不可以串"）

- 现有同步架构本来就是**按 user_id 隔离**的（tasks/birthdays 表都有 user_id 列，令牌→userId）。
- 改造后：**会话令牌 → 账号 id → 作为 user_id**。不同账号天生看不到彼此数据，与现在令牌隔离机制同源，不需要迁移数据结构。
- 设备限制（已确认）：同一账号最多 **3 台**设备；超出后新设备登录被拒绝，必须先解绑释放额度；解绑入口在应用内「设置—账号—设备管理」（列表+解绑按钮），远端解绑后该设备令牌立即失效。

### 2.5 界面（应用内新增）

- 「待办设置」新增**账号**分组（放在"版本"下方）：
  - 未登录：登录/注册 入口（注册含邮箱验证码输入框）；
  - 已登录：邮箱 + 激活状态 + 退出登录 + 修改密码（需邮箱验证码）；
  - **设备管理**：显示当前绑定的设备（名称、最近活跃时间、本机标记），每台设备带「解绑」按钮，解绑立即释放额度；已达 3 台时登录新设备会提示"请先在设置中解绑一台设备"。
- 云同步分组与账号打通：登录后才允许云同步（同步令牌由登录自动获得，用户不再需要手动填 48 位令牌）。

### 2.6 邮箱验证码：风险点与免费发信渠道（已确认采用邮箱+密码）

**风险点（都会在实现里处理）：**

| 风险 | 说明 | 对策 |
|---|---|---|
| 发信配额/成本 | 免费渠道都有每日限额 | 验证码邮件极短，免费额度（100~300 封/天）远超早期需求；超限后返回友好提示稍后再试 |
| 垃圾箱/送达率 | 海外发信方发往 QQ/163 邮箱可能进垃圾箱 | 配置 SPF/DKIM；邮件文案注明"若未收到请检查垃圾箱"；备选国内阿里云邮件推送 |
| 验证码爆破 | 6 位码可被穷举 | 10 分钟过期 + 最多 5 次尝试 + 存 hash 不存明文 |
| 恶意刷接口 | 用你的免费配额狂发邮件 | 同邮箱 60 秒 1 封、同 IP 每小时 10 封、注册接口加图形验证可后置 |
| 合规 | 收集邮箱属个人信息 | 注册页隐私声明一句话："邮箱仅用于账号验证与找回密码"；密码 PBKDF2 存储 |

**免费发信渠道对比（选一个接入，均在 Worker 内调用 API/SMTP）：**

| 渠道 | 免费额度 | 到达率(国内) | 接入难度 |
|---|---|---|---|
| **Resend（推荐）** | 100 封/天，3000 封/月 | 中等（需配 SPF/DKIM） | 最低：一个 fetch 调用，10 分钟接入 |
| Brevo | 300 封/天 | 中等 | 低：HTTP API |
| 阿里云邮件推送 | 每日前 200 封免费，超出约 2 元/千封 | **最好**（国内服务器发信） | 中：需验证发信域名+SDK |
| QQ/163 邮箱 SMTP 授权码 | 不透明、易被风控 | 好 | 低但不适合产品化，仅测试用 |

**推荐路线**：先用 Resend 起步（零成本、接入最快）；若用户反馈验证码收不到/进垃圾箱，再切阿里云邮件推送（接口抽象一层，切换只改一个函数）。

## 三、买断制激活方案（推荐：激活码）

### 3.1 为什么选激活码（而不是纯账号付费）

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 激活码（推荐）** | 你可生成后在小红书私信/自动发货平台售卖，无需支付资质；可控制发行量、可吊销退款 | 需要做发码和核销逻辑（约 100 行） |
| B. 卡密平台代发（发卡网） | 全自动发货 | 手续费 3~6%，平台跑路风险，体验不可控 |
| C. 接微信支付 | 用户自助购买 | 需要企业资质/个体户，周期长，现阶段不现实 |

**推荐 A**：先手工/半自动发码起步（小红书成交后发码），量大后再接发卡平台自动化，激活码体系不变。

### 3.2 激活码设计

- 格式：`TK-XXXX-XXXX-XXXX`（Crockford Base32，去掉易混淆的 0/O/1/I），服务端随机生成，查表核销。
- 生命周期：`unused → used（绑定账号）→ revoked（退款/黑名单时吊销，账号恢复未激活）`。
- 一码一账号，绑定后不可转移（换机不受影响——绑定的是账号不是设备）。
- 生成方式：提供管理接口（见 3.4），也可离线脚本批量生成后导入。

### 3.3 试用与门禁（✅ 已确认：方案①）

- **14 天全功能试用 + 激活永久解锁**
  - 未注册/未激活：安装后 14 天内全功能可用（本地记录试用天数，联网校验）；
  - 到期后本地功能锁定（只能查看不能新增/编辑），云同步直接停用；
  - 已激活：永久全功能，离线也可用（每 7 天联网校验一次激活状态，断网宽容期 30 天）。
  - 优点：先体验后付费转化率高；破解者绕过客户端也拿不到云同步。

### 3.4 管理后台（极简，用管理令牌保护）

| 接口 | 说明 |
|---|---|
| POST /api/admin/codes/generate | `{count, batch}` 批量生成，返回码列表（导出即可发货） |
| GET /api/admin/codes?status= | 查询码状态 |
| POST /api/admin/codes/revoke | 吊销某码（退款用） |
| POST /api/admin/users/disable | 封禁账号 |

管理令牌存 Worker 环境变量（ADMIN_TOKEN），只在你自己手里。

## 四、老用户与数据迁移

1. 部署新 Worker（自动建 users/sessions/activation_codes 表，现有 tasks/birthdays 不动）。
2. 你自己的老令牌数据：用一次管理接口 `POST /api/admin/migrate` 把旧 user_id 的数据并入你的账号（写个一次性脚本）。
3. 已发布的手动令牌方案：老版本继续可用（Worker 保留令牌校验兼容层），新版本用登录。等你全部换到新版本后可下线兼容层。
4. 用户换电脑：登录账号 → 自动拉取云端数据，无缝。
