# 邀请有礼（自裂变）功能 — 产品需求分析方案

> 状态：需求分析稿（不改动代码）
> 基于现有架构梳理：桌面端 Tauri App + Cloudflare Worker(`sync-worker`) + D1 数据库 + 单文件后台 `release/admin/index.html`。
> 涉及代码锚点：注册接口 `sync-worker/src/index.ts:516`、会员激活 `sync-worker/src/admin.ts:369`（`UPDATE users SET activated=1`）、后台菜单 `release/admin/index.html:668 NAV` 数组、前端会员判定 `src/membership.ts`。

---

## 一、需求必要性

**1. 降低获客成本，构建自裂变闭环。**
当前产品获客主要依赖外部渠道（小红书等）。邀请有礼让**已注册用户成为获客节点**：每带来一个新注册/新会员，邀请人得奖励，形成"用户拉用户"的复利增长，边际获客成本趋近于 0。

**2. 与会员变现直接挂钩。**
Tacco 的商业化核心是会员（记录排序、云存储、长辈模式、数据导出、成长报告）。奖励设成"X 天会员"或"X 元现金"，既激励老用户传播，又把新用户导入会员体系（被邀请人注册后易转化为会员），形成"拉新 → 体验 → 付费"的漏斗。

**3. 后台可配置，活动可控、风险可管。**
奖励方式/数量/触发条件/预算全部后台可配，可随时开关活动、设上限，避免无限补贴；现金提现走"上传收款码 + 后台审核 + 人工转账"，资金可控、无自动打款风险。

**4. 平台特性适配（需注意）。**
Tacco 是**桌面端工具**，没有移动端的"一键分享到微信联系人"能力，裂变链路弱于 App。但桌面用户本就活跃在微信/QQ 群（工作人群），**"复制链接 → 粘贴到聊天 → 对方电脑打开下载 → 注册时填邀请码"** 的链路是成立的。方案据此把"邀请码粘贴"作为归因主路径，分享仅为便利。

## 二、前置决策（已确认，本次固化）

### 决策 A：会员限时模型 → **已选【方案 B】**
- **现状**：`users.activated` 是布尔值（0/1），会员=永久，无到期时间。
- **方案 B（采用，需小重构）**：新增 `membership_expires_at` 字段，`isFullAccess` 判定改为 `activated=1 && (membership_expires_at IS NULL || membership_expires_at > now)`——即 `NULL` 表示永久会员，有值表示限时会员。邀请奖励、激活码、后台手动激活统一写入该到期时间。一次性把会员模型升级为"可限时/可永久"，后续所有赠送逻辑都干净。
- **已知限制（写入方案，不再回避）**：若用户已是**永久会员**（`expires_at IS NULL`），再获得"X 天会员"奖励时应如何处理——本方案采用「**限时天数叠加到永久会员不生效，改为发放等价现金券/或不发放并提示**」的保守策略，避免"永久被限时覆盖"或"天数无意义累加"。具体在发奖函数 `grantInviteRewards` 中：`days` 类型仅当目标用户当前为限时会员或新用户时写入到期时间；永久会员命中 `days` 槽时，提示运营"该用户为永久会员，天数奖励已跳过"，不强行改写。此限制需在后台配置 UI 与用户端明确告知。
- 备选 A1（延长试用）已放弃，因其混淆"试用/付费会员"语义且老会员拿不到天数。

### 决策 B：奖励结构 → **已选【多奖励槽 + 阶梯奖励】一步到位**
- 每个活动支持配置**多个"奖励槽"（slot）**，每个槽独立指定：作用对象（邀请人 / 被邀请人）、奖励类型（会员天数 / 现金）、数值、触发条件。
- 同时支持**两种发放策略**：
  - `flat`（扁平）：每个有效邀请按固定槽组发奖。
  - `tiered`（阶梯）：按**邀请人累计有效邀请数**分档，不同档位套用不同奖励组（支持"满 N 人额外一次性奖励"，如满 10 人额外发 ¥20）。
- 典型组合示例（一步到位）：
  - 槽1：被邀请人·注册即送·3 天会员（trigger=register, target=invitee）
  - 槽2：邀请人·被邀请人成为会员·送 5 元现金（trigger=member, target=inviter）
  - 阶梯：邀请人累计满 10 人 → 额外一次性奖励 10 元现金

### 决策 C：触发条件 → **已选【双触发同时支持】**
- 活动可**同时开启**「注册即奖励」与「成为会员才奖励」两条触发链，由每个奖励槽各自的 `trigger_on` 决定该条奖励挂在哪个事件上（见决策 B 示例）。
- 发奖在两类事件发生时分别触发：① 注册成功（`register` 槽）；② 被邀请人会员激活（`member` 槽，复用现有 `redeemActivationCode` 钩子）。

## 三、数据模型（支持多奖励槽 + 阶梯，方案 B/C 落定）

### 1. 活动配置表 `invite_activity_config`
| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键（仅 1 条生效，单活动模型；多活动并行需加 `status` 与 `priority`，V1 单活动） |
| enabled | bool | 活动总开关 |
| reward_strategy | enum | `flat` / `tiered`（决策 B） |
| max_per_inviter | int | 单邀请人最多有效邀请数（防刷，默认 100） |
| budget_cap_cents | int/null | 总现金预算上限（可选，监控 + 触顶停发） |
| start_at / end_at | datetime/null | 活动有效期（null=长期） |
| updated_at | datetime | 修改时间 |

### 2. 奖励槽表 `invite_reward_slots`（多槽核心）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键 |
| activity_id | int | 所属活动 |
| tier_id | int/null | 归属阶梯档位（flat 模式为 NULL；tiered 模式指向 `invite_tiers.id`） |
| target | enum | `inviter` / `invitee`（奖励发给谁） |
| reward_type | enum | `days` / `cash` |
| value | int | 天数（days）或分（cash） |
| trigger_on | enum | `register` / `member`（决策 C，双触发各自挂槽） |
| sort_order | int | 展示顺序 |

### 3. 阶梯档位表 `invite_tiers`（仅 tiered 模式）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键 |
| activity_id | int | 所属活动 |
| min_invites | int | 累计有效邀请数达到该值进入本档（如 10） |
| label | text | 档位名（如"达人""合伙人"） |
| bonus_once | bool | 是否仅首次达到时一次性发放（true=满档额外奖，false=之后每单按本档发） |

> 发奖时取 `min_invites <= 邀请人累计有效数` 的**最高档**；`bonus_once=true` 的槽通过 `invite_rewards.tier_bonus_awarded` 标记防止重复。

### 4. 邀请关系表 `invitations`
| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键 |
| inviter_id | text | 邀请人 user.id |
| invitee_id | text | 被邀请人 user.id |
| invite_code | text | 使用的邀请码（冗余，便于审计） |
| status | enum | `registered` / `member` / `rewarded`（聚合态，明细见 `invite_rewards`） |
| valid | bool | 是否计入邀请人"有效邀请数"（会员激活后置 true） |
| created_at | datetime | 注册时间 |

> 唯一约束 `(invitee_id)`：**一个被邀请人仅首次注册可绑定一次邀请人**，防重复/篡改。

### 5. 发奖明细表 `invite_rewards`（防重复 + 审计 + 提现溯源）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键 |
| invitation_id | int | 关联邀请 |
| slot_id | int | 触发的奖励槽 |
| user_id | text | 实际收款人（inviter 或 invitee） |
| reward_type | enum | `days` / `cash` |
| value | int | 天数或分 |
| tier_id | int/null | 若来自阶梯额外奖则记录档位 |
| created_at | datetime | 发奖时间 |

> **唯一约束 `(invitation_id, slot_id)`**：一次邀请事件对同一槽只发一次，杜绝双触发/重入导致重复发奖。现金奖励入账后写入 `users.withdrawable_balance_cents`。

### 6. 提现申请表 `withdrawals`
| 字段 | 类型 | 说明 |
|---|---|---|
| id | int | 主键 |
| user_id | text | 申请人 |
| amount_cents | int | 提现金额（分） |
| alipay_account | text | 支付宝账号（手机号/邮箱） |
| alipay_name | text | 真实姓名（与支付宝实名一致，转账校验用） |
| alipay_qr_url | text | 收款码图片地址（R2 或 base64，见下） |
| status | enum | `pending` / `approved` / `rejected` / `paid` |
| review_note | text/null | 审核备注 |
| reviewed_by / reviewed_at | text/null / datetime | 审核人/时间 |
| created_at | datetime | 申请时间 |

> **合规注意**：`alipay_account` / `alipay_name` / `alipay_qr_url` 属敏感金融个人信息，落库须加密（至少字段级 AES），传输全程 HTTPS，后台访问须管理员 token（已实现）。详见第八、九节。

### 7. `users` 表改动
- 新增 `membership_expires_at`（决策 A-B；NULL=永久会员，有值=限时到期时间）。
- 新增 `withdrawable_balance_cents`（可提现余额）。
- 新增 `invite_code`（每个用户稳定邀请码，注册生成，唯一）。

### 8. 收款码图片存储
- 前端上传 `data:image/...`（限 300KB，与头像一致），Worker 转存 **R2 对象存储**（若已有 R2 绑定复用；否则降级 base64 文本列，限 300KB）。后台审核页展示图片（点击放大）。

## 四、后端接口（新增/改动）

### 注册接口改动 `POST /api/auth/register`
- 请求体新增可选字段 `inviteCode?: string`。
- 逻辑：注册成功后，若 `inviteCode` 有效（存在、非本人、对应活动 `enabled`、未超 `max_per_inviter`、在有效期内），插入 `invitations`（status=`registered`，valid=false）。
- **注册即奖励（trigger_on=register 的槽）**：调用 `grantInviteRewards(invitation, 'register')`，遍历匹配 target 的槽发奖；`invitations.status` 推进到 `rewarded`（仅代表"注册链已发"，member 链仍待激活）。
- 防刷：V1 至少保证"被邀请人必须新注册 + `invitee_id` 唯一"；同设备指纹短时多注册列为 V2 风控。
- **自我邀请拦截**：`inviteCode` 解析出属于自己的码 → 忽略，不绑定。

### 会员激活钩子（发奖关键路径）
- 在 `redeemActivationCode`（`sync-worker/src/admin.ts:369`，`UPDATE users SET activated=1`）成功后：
  1. 将该 `invitations.valid=true`（计入邀请人有效邀请数），status 推进到 `member`。
  2. 调用 `grantInviteRewards(invitation, 'member')` 发放 `trigger_on=member` 的槽（flat：tier_id=null 的槽；tiered：按邀请人累计有效数选最高档）。
  3. 写 `invite_rewards` 明细，status 置 `rewarded`。
- 后台手动激活 `/api/admin/users/activate` 同样触发该钩子（一致性）。

### 统一发奖函数 `grantInviteRewards(invitation, event)`
- `event` ∈ {`register`, `member`}，匹配 `trigger_on` 相同的槽。
- 取槽集合：flat 取 `tier_id IS NULL`；tiered 取 `min_invites <= 邀请人累计有效数` 的**最高档**所属槽（含 `bonus_once` 一次性奖，用 `invite_rewards.tier_id` 去重）。
- 对每条槽，按 `target` 决定收款人（inviter / invitee）：
  - `days`：若收款人为限时会员或新用户 → 写 `membership_expires_at = max(now, 现有到期) + value 天`；若为**永久会员**（`expires_at IS NULL`）→ **跳过并记日志**（决策 A 已知限制，避免天数无意义）。
  - `cash`：`withdrawable_balance_cents += value`，并落 `invite_rewards` 明细（用于审计与提现溯源）。
- **防重复（幂等）**：每条发放以 `(invitation_id, slot_id)` 唯一约束保证——钩子重入、双触发竞态、`redeem` 与后台激活并发均安全，绝不会重复入账。

### 用户侧接口
| 接口 | 说明 |
|---|---|
| `GET /api/invite/my` | 返回 `inviteCode`、`inviteLink`、`stats{invited, registered, members, rewarded}`、`balanceCents`、`earnedDays` |
| `GET /api/invite/records?page&pageSize` | 我的邀请记录列表 |
| `POST /api/invite/withdraw` | 提现申请 `{amountCents, alipayAccount, alipayName, alipayQr(dataURL)}`；校验余额≥金额、金额>0、信息完整 |
| `GET /api/invite/withdrawals` | 我的提现记录 + 状态 |

### 后台接口（需管理员 token）
| 接口 | 说明 |
|---|---|
| `GET/POST /api/admin/invite/config` | 读写活动配置；POST 体含 `config` + `slots[]` + `tiers[]`，事务写入（删旧 upsert），返回完整配置供前端回显 |
| `GET /api/admin/invite/records` | 全量邀请记录（支持按邀请人/状态筛选、导出） |
| `GET /api/admin/invite/withdrawals` | 提现审核列表（支持状态筛选） |
| `POST /api/admin/invite/withdrawals/:id/review` | `{action:'approve'|'reject'|'paid', note?}`；`paid` 时校验余额未被重复扣减，置 `paid` 并扣减 `withdrawable_balance_cents` |

## 六、邀请人与被邀请人关联逻辑

```
[邀请人] 会员中心 → 复制链接/码 ──(微信/QQ)──▶ [被邀请人]
                                                  │
                                  打开链接 / 直接下载安装 App
                                                  │
                                  注册页填写邀请码（或粘贴链接自动提取）
                                                  │
                              POST /api/auth/register {inviteCode}
                                                  │
                                  后端绑定 invitations(inviter,invitee,status=registered)
                                                  │
                          ┌───────────────────────┴───────────────────────┐
                   trigger_on=register                              trigger_on=member
                          │                                                │
                  立即 grantInviteRewards                         等待被邀请人激活会员
                          │                                       (redeemActivationCode 钩子)
                          │                                                │
                   status=rewarded                                  grantInviteRewards
                                                                       status=rewarded
```

**边界与风控**
- 被邀请人必须是**新注册账号**（按 `invitee_id` 唯一约束防重复绑定）。
- 邀请码解析为本人 → 自动忽略（防自刷）。
- `max_per_inviter` 超限 → 不再发奖（仍记录绑定，状态保持 `registered`）。
- 同一设备指纹短时间内大量注册 → V2 增加风控；V1 至少保证"一个被邀请人只计一次"。
- 活动 `disabled` 或超期 → 不绑定、不发奖。
- 现金奖励需防"小号刷奖励→提现"：除设备风控外，建议提现设最低额度（如 ¥10）与审核人工核对，必要时要求被邀请人已激活会员才允许邀请人提现对应奖励。

## 七、后台管理（新增菜单与页面）

在 `release/admin/index.html` 的 `NAV` 数组（第 668 行）新增菜单项：

```
{ hash: '#/invite', label: '邀请有礼', icon: '<svg…/>' }
```

该菜单下用 Tab 切换三个子视图（单页内实现，沿用现有单文件 SPA 模式）：

### 1. 活动配置 Tab
**顶部（活动级，对应 `invite_activity_config`）**：
- 活动开关（启用/停用）
- 发放策略：`flat` 扁平 / `tiered` 阶梯（单选）
- 单邀请人上限（有效邀请数，防刷）
- 总现金预算上限（元，可选；触顶自动停发现金）
- 活动起止时间（可选）

**奖励槽编辑器（多槽核心，对应 `invite_reward_slots`）**：动态增删的卡片列表，每行字段：
- 作用对象：`邀请人` / `被邀请人`（target）
- 触发条件：`注册即奖励` / `成为会员才奖励`（trigger_on，决策 C 双触发各自挂槽）
- 奖励类型：`会员天数` / `现金`（reward_type）
- 数值：天数输入框 / 金额输入框（元）
- 归属档位：仅 tiered 模式显示下拉，选「默认档」或某阶梯档（tier_id）

**阶梯管理器（仅 tiered 模式显示）**：动态增删档位，每个档位字段：
- 档位名（如「达人」）
- 触发阈值（累计有效邀请数，如 10）
- 奖励方式：`每单按本档发` / `仅首次达到时一次性发`（bonus_once）
- 该档下的奖励槽（复用上面的槽编辑器，tier_id 指向本档）

**保存** → `POST /api/admin/invite/config`（事务写入 config + 全量 slots + tiers，删旧写新或 upsert）。

> 配置示例（后台所见即所得）：
> - 槽① 被邀请人 / 注册即奖励 / 会员天数 3 天
> - 槽② 邀请人 / 成为会员才奖励 / 现金 ¥5
> - 阶梯档「达人」min=10 → 槽③ 邀请人 / 成为会员才奖励 / 现金 ¥10（bonus_once，首达额外奖）

### 2. 邀请记录 Tab
表格列：邀请人（邮箱/昵称）、被邀请人、邀请码、触发条件、奖励类型、奖励值、状态（注册中/已会员/已奖励）、发奖时间、注册时间。
筛选：按邀请人、状态；复用现有导出能力（Excel/txt）。

### 3. 提现审核 Tab
表格列：申请人、金额、支付宝账号、姓名、收款码（缩略图，点击放大）、状态、申请时间、审核备注。
操作（每行）：
- 「通过并标记已转账」→ 校验余额，置 `paid`，扣减 `withdrawable_balance_cents`，记录审核人。
- 「驳回」→ 填驳回原因，置 `rejected`。
- 顶部统计：待审金额合计、已支付合计，辅助财务对账。

## 八、风险与漏洞深度分析

> 本功能涉及资金反向流动（开发者→用户）+ 敏感个人信息（金融账号）+ 会员模型重构，风险面较宽。以下按"技术正确性 / 资金安全 / 合规隐私 / 业务边界"四类展开，并给出缓解措施。**未解决前不得进入开发。**

### A. 发奖正确性与幂等（技术核心）
- **多槽 × 双触发的重复发奖**：一次邀请可能触发多个 slot（如槽①注册送被邀请人、槽②会员送邀请人），且 `register` 与 `member` 是两次不同事件。必须靠 `invite_rewards` 的 **`(invitation_id, slot_id)` 唯一约束**兜底，钩子任何重入（并发 `redeem` + 后台手动激活）都不会重复入账。
- **阶梯一次性奖（bonus_once）重发**：被邀请人反复激活/取消会重复触发 member 事件。需以 `invite_rewards` 中是否已存在该 `(invitation_id, slot_id, tier_id)` 去重，并仅在"邀请人累计有效数首次跨过阈值"时发放。
- **限时累加语义**：`days` 奖励必须 `expires_at = max(now, 现有到期) + value`，**不可重置**为 `now+value`，否则老会员续期被清零。
- **永久会员命中 days 槽**：决策 A 已知限制——`expires_at IS NULL` 的永久会员跳过 days 奖励并记日志，不强行改写（避免"永久被限时覆盖"）。发奖时应以**收款人当前状态**判定，而非邀请人。

### B. 资金与薅羊毛（现金奖励独有）
- **小号刷现金**：批量注册小号 → 邀请人拿现金 → 提现。缓解：① 现金奖励优先挂在 `trigger_on=member` 槽（需被邀请人真激活会员，提高成本）；② 设提现最低额（如 ¥10）；③ 同设备指纹/IP/支付宝实名关联检测，超限进风控名单；④ `max_per_inviter` 限制有效邀请数。
- **预算失控**：多槽 + 阶梯 + 现金，单次活动现金总支出可能超预算。`budget_cap_cents` 触顶后**自动停发现金**（仍记录绑定但不打钱，提示"活动预算已用尽"），而非硬报错中断。
- **提现欺诈**：收款码与姓名不一致、盗用他人码。审核人工核对"姓名↔支付宝实名"，驳回并重查该邀请链路。

### C. 合规与隐私（敏感个人信息，最高优先级）
- 支付宝账号 + 真实姓名 + 收款码 = **敏感金融个人信息**（国内《个人信息保护法》列为敏感信息，需"单独同意"；微软商店 10.5 列为高度敏感）。缓解：
  - 落库**字段级 AES 加密**，`withdrawals` 表三字段密文存储；传输全程 HTTPS；后台访问强制管理员 token（已具备）。
  - **隐私政策更新**：明确告知收集哪些金融信息、用途、保留期限、与谁共享（不共享，人工转账仅内部）。
  - **单独同意弹窗**：提现申请前弹出"收集支付宝账号/姓名/收款码用于发放奖励"的单独授权，不能复用注册时的一揽子同意——这是法律硬性要求，不是 UX 优化。
  - 最小保留：转账完成并过凭证留存期后，删除收款码原图（保留脱敏的转账凭证记录）。

### D. 归因失效（桌面端结构性）
- 用户复制链接但注册时未粘贴 → 关系不建立，双方无奖励。技术上无法跨应用强制携带。缓解：① 落地页把 CODE 暂存 localStorage，注册页自动预填（仅优化同设备/同浏览器）；② 文案与弹窗反复教育"注册时填邀请码双方都得奖励"；③ 邀请人端展示"已分享、待注册"中间态，降低误以为"已邀请成功"的预期。

### E. 传销边界（业务红线）
- 方案严格限定**一级返利**（邀请人得奖；被邀请人再邀他人，原邀请人不二次得奖）。阶梯是"按自己累计数提高自身奖励"，非"发展下线分级抽成"，**不构成传销**（《禁止传销条例》三级及以上分销才构成）。
- 产品文案禁用"团队""下线""躺赚""无限代"等词；后台数据看板仅展示"我的邀请"，不展示层级网络图（避免被解读为传销架构）。

### F. 会员模型重构成本
- 决策 A-B 涉及 `isFullAccess` 判定、`src/account.ts` 快照、`redeem`/`activate` 全链路、`membership.ts`。需回归测试（现有 `admin.test.ts` 已有 redeem 用例，必须补 invite 用例覆盖：永久会员命中 days、限时累加、双触发、阶梯越级）。迁移脚本：现有 `activated=1` 且无 `expires_at` 的用户**保持 NULL=永久**，不回填。

### G. 提现图片存储
- 确认 Worker 的 R2 绑定；若无，降级为 base64 文本列并限 300KB。后台审核页点击放大预览。

## 九、应用市场上架影响分析（基于真实政策）

> 目标平台：微软商店（Microsoft Store，当前 `MAC_OPEN=false` 仅 Windows 主推，store 提交的是 NSIS `.exe` 离线包）+ 自分发下载站（`todobar-app.app.workbuddy.host`）。Mac App Store 因 Tauri 沙盒/无自更新限制，当前不计划上架（走自分发）。

### 9.1 微软商店（Microsoft Store Policies v7.20，2026-10-22 生效）
- **10.5 Personal Information（关键条款）**：收集/存储/传输个人信息须现代加密；**不得收集高度敏感个人信息（如健康/金融数据），除非与产品功能相关**；须取得明确用户同意；隐私政策须清晰说明收集时机、原因、用途。
  - 我们收集支付宝账号/姓名/收款码属"金融数据"。**与产品功能相关**（提现发奖使其相关）→ 合规，但必须满足：加密存储 + 单独同意 + 隐私政策披露。
  - **硬性动作 1**：更新隐私政策 URL（提交商店必填项），新增"邀请奖励提现所收集的金融信息"章节。
  - **硬性动作 2**：提现前单独同意弹窗（见第八节 C）。
- **10.8 Financial Transactions（另一关键条款）**：游戏必须用微软 IAP；**非游戏 PC 应用可用安全第三方购买 API 或微软 IAP**。
  - 我们的关键优势：**全程不集成任何支付/打款 SDK**——会员靠激活码、现金靠人工支付宝转账。因此**不触发 10.8.1「必须用微软 IAP」强制**。反向打款 + 人工审核反而规避了最严格的 IAP 条款。
  - 但"捕获金融信息"（收集支付宝账号）仍需 10.5 披露。
- **10.1 / 反欺诈**：邀请奖励须真实发放，不得虚假宣传"稳赚/躺赚"。文案避免夸大收益。
- **10.1.4 / 10.8**：商店描述需披露"应用内含奖励/购买功能"。
- **提交格式**：`.exe`/`.msi` 离线安装、不捆绑无关软件（NSIS 合规）；收集个人数据时**必须提供隐私政策 URL**。
- **结论：不会因此功能被拒**，但有 3 个硬性合规动作（隐私政策更新、单独同意、商店描述披露），均可在提交审核前单独完成，与功能代码正交。

### 9.2 Mac App Store（若未来上架）
- 当前 `MAC_OPEN=false`，且 Tauri 应用上 Mac App Store 需沙盒强制、无内置更新、须 Xcode 打包——实际走自分发（下载站），本功能不影响。
- 若未来上架：同样需隐私政策披露 + 沙盒下收款码存 App container（合规）；Mac App Store 明确**禁止"提供到期内容或服务"作为应用卖点**。限时会员若被解读为"到期服务"有歧义——建议 Mac 上架时把限时奖励表述为"赠送会员时长/权益"，避免强调"订阅到期"，且永久会员为主、限时仅为赠送，不触发该条。

### 9.3 总体结论
- **邀请有礼 + 现金提现不阻断上架**微软商店或自分发；核心合规动作是「隐私政策 + 单独同意 + 商店描述披露」，均与代码功能正交，可在上架前单独处理。
- 真正需要谨慎的是**国内运营侧**（反洗钱/税务凭证留存、传销边界），与商店审核无关，但影响业务可持续性——见第八节 B/E。

## 十、实施建议（阶段）

因决策 B/C 要求"一步到位"，不再按奖励类型分期，而是**每一层都一次性支持多奖励槽 / 阶梯 / 双触发**，按依赖顺序分里程碑（每个里程碑都已是完整多槽能力）：

- **M0（数据 + 会员模型重构）**：新增 6 张表（`invite_activity_config` / `invite_reward_slots` / `invite_tiers` / `invitations` / `invite_rewards` / `withdrawals` 改动）；`users` 加 `membership_expires_at` / `withdrawable_balance_cents` / `invite_code`；`isFullAccess` 升级为"可限时/可永久"；回归测试覆盖永久会员命中 days、限时累加、双触发、阶梯越级。
- **M1（发奖引擎）**：`grantInviteRewards(invitation, event)` 多槽 + 阶梯 + 双触发 + 幂等唯一约束；注册接口绑定；会员激活钩子（redeem + 后台激活）发奖。
- **M2（App 端）**：邀请主页（复制链接/码、统计、记录）、注册页邀请码输入、升级弹窗 CTA、会员中心入口。
- **M3（后台）**：NAV 新增「邀请有礼」菜单；活动配置（多槽 + 阶梯编辑器）、邀请记录（含导出）、提现审核（收款码预览、通过/驳回、资金统计）。
- **M4（现金闭环）**：提现申请（含单独同意弹窗 + 字段加密）+ 审核打款 + 余额扣减 + 预算触顶停发。
- **M5（体验与风控加固）**：邀请海报、落地页预填、风控（设备/IP/实名关联）、提现最低额、转化漏斗看板（复用现有 funnel 组件）。
- **上架前合规动作（与代码并行）**：更新隐私政策（金融信息章节）、准备单独同意弹窗文案、商店描述披露奖励功能。
